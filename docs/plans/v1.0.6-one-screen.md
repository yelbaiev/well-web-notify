# One settings screen, plus a log

## The premise I got wrong

I gave this plugin the shape of Well Web SEO: a top-level menu, sidebar rows
per section, one screen each. SEO has eighteen screens across six sections and
earns that. Notify has four channels, one list of form plugins, six order
checkboxes, one country code, and a log.

That is one settings screen and a log. Splitting it into three meant:

- three sidebar rows for a plugin you configure once,
- two settings groups instead of one, purely because two forms on one group
  would null each other's checkboxes (see `admin-settings.php`) — a workaround
  for a structure that did not need to exist,
- a Channels screen that could not tell you whether anything had been
  delivered, and a Log screen that could not tell you why not.

## What it becomes

**One settings screen with three sections and a sticky index beside them** —
the same pattern as Well Web SEO's own Settings screen, which is where that
plugin puts the things you set once rather than the things you work in — plus
**one more sidebar row for Activity**.

Two rows, not four. Activity is the exception for a concrete reason, below.

Each screen or section answers exactly one question:

| Where | Question |
|---|---|
| Settings ▸ Channels | Where do notifications go? |
| Settings ▸ Sources  | What sets one off? |
| Settings ▸ Message  | How does it read when it arrives? |
| Activity            | Did it work? |

### Why Activity is not a section

It was one, briefly. Its filters and its pager are GET navigations that reload
the page — which on a settings screen means quietly discarding whatever was
half-typed into a credentials field. Data you page through does not belong
inside a form you save.

The settings screen keeps one pointer to it: a strip that appears **only when
something has actually failed**, so a site whose notifications have started
bouncing still says so on the screen people open.

**Message, not Sources, owns the country code.** The dialling code is not a
trigger — it is how the phone number is rendered in the message that gets sent.
Putting it under Sources was filing it by the screen that had room, and it left
Message with nowhere to grow when the next "what goes in the message" option
turns up.

## Sections, not tabs

The user offered both. Sections win here for three reasons:

1. **Tabs are the same navigation, moved.** Three server renders and a strip of
   three links is what the sidebar already was. Nothing is gained.
2. **One Save button.** With tabs, switching tabs mid-edit either loses changes
   or needs per-tab forms and per-tab saves. With one page there is one form
   and one button, and "did I save that?" stops being a question.
3. **It is the sibling plugin's own answer.** Well Web SEO absorbed five
   screens into one Settings page with a sticky sub-nav in 2.25.x. Matching it
   is the point of sharing a design system.

## One settings group again

The settings screen carries one `<form method="post" action="options.php">`
covering Channels, Sources and Message — therefore **one settings group**, which
undoes the two-group split from the three-screen version. That split existed
only because `wp-admin/options.php` walks every option registered to the
submitted group and passes `null` for the ones absent from the request — so
saving Sources switched off every channel. With one form nothing is absent, and
the workaround goes away with the structure that caused it.

Activity carries a `<form method="get">` for its filters. Read-only, so no
nonce.

## Slugs

`well-web-notify-settings` and `well-web-notify-log` both keep the slugs they
have had since 1.0.0 — the settings screen and the log respectively. Only the
slug invented during the three-screen version is retired:

| Was | Goes to |
|---|---|
| `well-web-notify-sources` | `well-web-notify-settings#sources` |

302, not 301 — an admin screen behind a login should not leave a permanent
redirect in a browser cache that cannot be undone if a slug is ever reinstated.
